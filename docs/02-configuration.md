# Project configuration

Defined by `config/generator.schema.json` (JSON Schema 2020-12) and the example `config/murcia-belluga.example.json`.

## Validation

```bash
.venv/bin/python -m onward_generator validate-config config/murcia-belluga.example.json [--json]
```

Exit codes: `0` valid, `1` invalid, `2` usage error.

Validation has three steps:

1. **Strict read** (`config/loader.py`). The file must be `.json`, UTF-8, at most 1 MB (a scene manifest or a `heights_overrides` file, which the pipeline writes, at most 64 MB), with an object at the root, no duplicate keys, and no `NaN` or `Infinity`.
2. **Schema.** Unknown fields are refused (`additionalProperties: false`). Types, ranges, and enums are strict. Every error is reported, each with its JSON pointer (`/area/margin_m`).
3. **Semantic rules** (`config/validation.py`), only after the schema passes:

| Code | Severity | Rule |
| --- | --- | --- |
| `center_incomplete` | error | Latitude and longitude must both be numbers or both `null` |
| `area_undefined` | warning | With no centre and no `boundary_file`, the geographic pipeline cannot run. Valid as a template |
| `center_outside_crs` | error | The centre falls outside the area of use of `area.crs` (EPSG:25830 when the field is absent) |
| `boundary_not_found` / `boundary_invalid` | error | `boundary_file` is missing, or it is not a valid WGS84 GeoJSON Polygon |
| `margin_mismatch` | warning | `area.margin_m` differs from the GeoJSON `margin_m`. The configuration wins |
| `center_outside_boundary` | warning | The centre is outside the polygon |
| `export_adapter_unverified` | warning | `export.enabled: true` is valid, but `onward_unity` 0.1.0 has not passed the Quest acceptance test (`docs/12-export.md`) |
| `stage_not_implemented` | info | Enabled `generation` stages that do not exist yet |

Schema codes look like `schema_<keyword>`: `schema_minimum`, `schema_enum`, `schema_required`, `schema_additionalProperties`.

## One folder per map

`onward-generator map create` writes this configuration from a name and a WGS84 centre. The id and `maps/<id>` are the slug of that name (`Apocalipsis Murciana` becomes `maps/apocalipsis_murciana`). The folder holds `map.json`, `config/project.json`, `config/export.json` (card title, `build.lightmap_texels_per_m`, default 10, at most 40, and the room lights `build.interior_lights_max` 160 and `build.interior_light_intensity` 3.0; it never writes the opt-in lightmap keys `build.scenic_out_of_lightmap` (plan C4) and `build.lightmap_pages_max` (plan C5, an integer from 1 to 64 that lowers `lightmap_texels_per_m` until the lightmap estimate fits that many pages, never below 4 texels/m; [12-export.md](12-export.md#lighting)), nor the plan D5 spike keys `build.lit_normal_material` (one `facade_trim_*` material drawn with `PP_Opaque_Lit` and a derived normal map) and `build.lit_normal_strength` ([12-export.md](12-export.md#lit-normal-spike-plan-d5))), `config/texture_plan.json`, and `reference/aoi.geojson`. `map.json` keeps `core_radius_m` (`--core-radius-m`; by default 50 m inside the radius, at most 150, and none under a 100 m radius): the half-side of the playable core square, or `null` when the whole map is played (0, a value at or above `radius_m`, or a map created before the key existed). A core must be at least 50 m. It is read by `detail` through its `next:` line; later stages read the `core` block of `scene_detail.json` ([ADR-017](decisions/ADR-017-playable-core.md)). With `--core-target-triangles N` (`map create`, or `run` on a new map), `map.json` also gets `core: {"mode": "budget", "target_triangles": N, "max_half_side_m": M}`: the budget core, off unless asked for until a headset session validates it. N is an integer from 1000 to 2 000 000; M is `--core-radius-m` when given, else `radius_m − 50`, and must lie between 50 and `radius_m − 50`. A map without a playable core cannot have one. The target is set at map create: `run --core-target-triangles` on an existing map whose `map.json` records another target, or none, stops at the plan step and changes nothing. `core_radius_m` and the fog are written as without the key, and a map without it behaves as before. The `detail` `next:` line then carries `--core-radius-m M --core-target-triangles N`. The block is checked again whenever `map.json` is read: another mode (such as `polygon`), other keys or a value out of range stop the stage. `map.json` `sources` holds the `run --source` / `--no-source` switches per source plugin, for example `{"es.catastro": false}`; a plugin without a switch runs wherever it covers the centre, except an opt-in plugin (plan D4: `nl.ahn`, `de.nrw_ndom`), which runs only with `"<id>": true` (`run --source <id>`), and still only inside its coverage. Any value is read as a boolean (`bool()`). `config/sources.json` holds the plugins' licence allowlist, the one priority that ranks height sources ([ADR-018](decisions/ADR-018-source-plugins.md)) and `evidence`, the one ranking of ground-floor shop evidence: `osm`, then `es.catastro`, then `overture` ([ADR-022](decisions/ADR-022-catastro-use.md)). `map.json` may also hold `"facades": {"mode": "trim" | "legacy", "style": "<name>" | "auto", "weathering": "clean" | "worn" | "heavy"}` (every key optional; `map create` does not write it): `run` passes it to `materials apply` as `--facades`, `--facade-style` and `--facade-weathering` (plan T2, [08-dress.md](08-dress.md#trim-sheet-facades)). Without it the facades use the trim-sheet atlas of the style chosen from the map centre ([ADR-020](decisions/ADR-020-trim-sheet-facades.md), `config/facade_styles.json`). Any other shape stops `run`. `map.json` may hold `"panoramax_atlas": true` (`map create --panoramax-atlas` writes it; absent or `false` is off, any other value stops `panoramax apply`): with `"panoramax": true` it packs the street-photo decals into one image per combine cell, tints the photographed trim walls and reports coverage ([01-pipeline.md](01-pipeline.md#8a-street-photos), ADR-020 amendment of 7 November 2026). `map.json` may hold `"regional_facades": true` (`map create --regional-facades` writes it; absent or `false` is off, any other value is refused with `MapError`): `run` then passes `--regional-facades` to `materials apply`, and `central_european`, `anglo` and `latin_american` take their trim atlas, window kinds and era bands from `config/facade_styles.regional.json` instead of the per-material path (plan D1, ADR-020 and ADR-027 amendments of 8 November 2026). `mediterranean` and `generic` maps are unchanged. Switching it on does not make `materials` stale, since freshness goes by file age: rerun from materials (`run --from materials`) after changing it. `map.json` may hold `"street_profile": true` (`run --street-profile` or `map create --street-profile`; absent or `false` is off, any other value is refused with `MapError`): `run` then resolves a street profile of enumerated ids with local Ollama before it plans the stages, writes `config/street_profile.json` (the record: raw reply, hashes, ids, changes; a stale one is kept as `config/street_profile.<sha>.json`) and, when a props profile applies, `config/street_profile_selection.json` (the `prop_selection` format), and passes the flags those ids stand for to `materials apply`, `overgrow place` and `perf cover` (plan D2, ADR-006 and ADR-010 amendments of 8 November 2026, [10-ai.md](10-ai.md#street-profile-plan-d2)). A named `facades.style`, `"repetition": true` or a `config/prop_selection.json` always wins over the profile. Off, nothing is read or written. `map.json` may hold `"lidar_roofs": true` (`map create --lidar-roofs` writes it; absent or `false` is off, any other value is refused with `MapError`): a LiDAR source plugin (`es.pnoa_ndsm`, `fr.lidar_hd`) then hands its `<id>_report.json` to `detail --lidar-roofs`, which draws a flat or pitched roof from each footprint's nDSM spread where no OSM roof tag does (plan C3, ADR-023 amendment, [07-detail.md](07-detail.md)). A map with no LiDAR plugin is unchanged. `map.json` may hold `"mid_ring_m": W` (`map create` does not write it; absent is off): W metres, 10 to 1000, of intermediate HLOD ring around the playable core, fixed or budget (plan D3, ADR-017 amendment of 9 November 2026, [07-detail.md](07-detail.md#intermediate-ring)). The `detail` `next:` line and `run` then pass `--mid-ring-m W` after the core flags. A value out of range, or the key on a map without a core, is refused with `MapError`. A changed, added or removed width makes `detail` stale. `map create` takes one flag per boolean switch of `map.json` (plan Q8): `--street-profile`, `--repetition`, `--overture-tints`, `--lidar-roofs`, `--regional-facades`, `--gameplay-report`, `--balanced-spawns`, `--sightline-cover`, `--panoramax-atlas`, `--wide-library`, `--normal-maps` and `--texture-variants`, each with its `--no-` form. Since 13 November 2026 a new map made from the command line has every switch on except `panoramax_atlas` (`maps.workspace.DEFAULT_OFF_SWITCHES`: it acts only with Panoramax, still under development), so a name, a centre and a radius are enough; `--no-<switch>` turns one off, and `run` takes the same flags for a new map and hands them to `map create`. A switch turned off is not written. Reading is unchanged: a `map.json` without the key, such as a map created before, has that switch off. With `--repetition` the texture plan is written with the calm pools at once, the plan `map create --textures` would write afterwards. `map.json` may hold `"wide_library": true` (`map create --wide-library` writes it; absent or `false` is off, any other value is refused with `MapError`): the texture plan then also draws on the 25 CC0 Poly Haven albedos of `config/dress/wide_library.json` (plan T1, [08-dress.md](08-dress.md)). With `--wide-library` the plan is written with them at once. `map.json` may hold `"normal_maps": true` (`map create --normal-maps`; absent or `false` is off, any other value is refused with `MapError`): `run` passes `--normal-maps` to `materials apply`, and the materials that draw a wide-library photograph get its real normal map on `PP_Opaque_Lit` (plan T3, ADR-039, [12-export.md](12-export.md#library-normal-maps-plan-t3)). `map.json` may hold `"texture_variants": true` (`map create --texture-variants`; absent or `false` is off, any other value is refused with `MapError`): `run` passes `--texture-variants` to `materials apply`, and building roofs and plaster walls get two more calm photographs, one per building by hash (plan T4, [08-dress.md](08-dress.md)). The projected CRS is EPSG:25830 in peninsular Spain and the UTM zone of the centre anywhere else. See [01-pipeline.md](01-pipeline.md).

## Paths

`area.boundary_file` is resolved from the configuration file's directory. The extension must be `.geojson`. The example points at `config/murcia_belluga_aoi.geojson`. A map created with `map create` points at `maps/<id>/reference/aoi.geojson`.

## From code

```python
from onward_generator.config import load_config, validate_config_file

config = load_config("config/murcia-belluga.example.json")  # GeneratorConfig or ConfigValidationError
config.area.center          # (lon, lat) or None
config.area.boundary_file   # absolute Path or None
```

`GeneratorConfig` and its sections are frozen typed dataclasses (`config/models.py`).

## Where the schema lives

The default is `config/generator.schema.json` at the repository root. `ONWARD_GENERATOR_SCHEMA` can point at another file.

## Natural language (phase 06)

`onward-generator ai plan` does not widen this contract. It writes copies of this configuration and of `heights.default.json` and `detail.default.json`, changing at most the whitelisted fields (`quality.detail_level` and `generation.interiors` on the project). Relative paths are rewritten to the same files, and the output is validated again with this schema. The area, the sources, the output path, optimisation, export, and the seed cannot change. See `docs/10-ai.md`.
