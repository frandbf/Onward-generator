# ADR-021 — Overture Maps places and buildings as third-party evidence

Status: accepted · 30 October 2026.

## Context

OpenStreetMap is the only source of shops and, outside Spain, of building heights. Many city blocks have no shop POI in OSM even where the street is lined with shops, so `detail` builds them as plain homes. Outside Spain there is no Catastro, and most OSM buildings have neither `height` nor `building:levels`, so `heights` falls back to type and neighbourhood estimates.

Overture Maps publishes, for the whole world, about 88 million places (Meta, Microsoft, Foursquare, AllThePlaces and others, each record with its own licence and a confidence) and a building theme (OSM, Microsoft and Google ML footprints, Esri, national agencies) with `height`, `num_floors`, colours and a `sources[]` list that names the dataset behind each property. Both are GeoParquet on S3, partitioned so that a bbox predicate on the `bbox` struct reads only the row groups that touch a map: a few hundred kilobytes for a 150 m map.

## Decision

1. **DuckDB is added as a dependency** (`duckdb==1.5.6`, MIT, `requirements.lock` and `pyproject.toml`). It reads the release GeoParquet over S3 with predicate pushdown and writes the clipped rows to a local parquet in one `COPY`. Its httpfs extension (MIT, signed by DuckDB) is installed in the Docker image at build time, so `overture fetch` does not download code at run time there; outside the image, the first fetch runs DuckDB's `INSTALL httpfs` once. Version 2.0.0 was released 9 days before this decision, so 1.5.6 (28 September 2026) is pinned.
   Alternatives considered:
   - **pyarrow + fsspec/s3fs.** Two larger dependencies (pyarrow alone is about 40 MB) for the same row-group pruning, and the bbox filter would be written against the dataset API instead of one SQL statement.
   - **Overture's own CLI (`overturemaps` on PyPI).** It wraps pyarrow and downloads one theme to GeoJSON or GeoParquet; it adds the same pyarrow weight, does not record per-record licences, and would be a second tool to pin.
   - **The Overture PMTiles or a tile API.** Tiles drop attributes (`sources[]`, `confidence`) that the licence record needs.
2. **`overture fetch --map DIR`** (network) resolves the release from the STAC catalogue (`https://stac.overturemaps.org/catalog.json`, field `latest`) unless `--release` is given, then writes `data/raw/overture_places.parquet` and `data/raw/overture_buildings.parquet`: every column of the rows whose bbox meets the map's inclusion square (the same WGS84 bbox as the Overpass request), ordered by id. Each file gets a `.source.json` sidecar: release, source glob, query, bbox, `retrieved_at`, row count, SHA-256, DuckDB version, the number of records per dataset and licence (from the whole-record entry of `sources[]`), and the attribution lines. A dataset whose records carry no licence (IGN, Google Open Buildings, Esri) gets the licence the Overture attribution page states, marked `license_origin: overture_attribution_page`. Nothing is overwritten without `--overwrite`, and both files are checked before any request. A failed read is tried again three times, waits doubling from 8 s; DuckDB's own HTTP layer also retries three times with a 120 s timeout.
3. **`overture match --scene --map --out`** (offline) writes `data/processed/overture/`:
   - `overture_places.json`: places with `confidence ≥ 0.7`, an `operating_status` of `open` or none (`accept_missing_status`, on by default: in Mexico City every place at that confidence had no status, so requiring `open` kept none; a closed place is always dropped), and a category that maps to one `shop`/`amenity`/`office`/`craft` tag (`config/overture.default.json`, `taxonomy.primary` first, then `basic_category`), in the scene's local grid, with `names.primary` as `name`, the dataset, the licence, and its attribution line. They are `attribute_origin: observed`, `observed_by: third_party`.
   - `heights_overrides.overture.json`: for each OSM building, the Overture footprint with the best intersection over union (at least `min_iou` 0.5; one Overture footprint per OSM footprint), with its `height` (inside the heights bounds) and `num_floors`. Each value keeps the dataset of its own property (the `/properties/height` or `/properties/num_floors` source, else the whole-record source). A value from OpenStreetMap is not lent (`skip_datasets`): it is already in the extract, and a copy ranked above `building:levels` would also take those buildings out of the neighbourhood median (measured in Mexico City: 62 neighbourhood estimates fell back to the category default). When height and floors come from different datasets, only the height is kept. A value whose licence is not on the `config/sources.json` allowlist (so also `unknown`) is not lent (`licence_not_allowed`). Each entry names its dataset, its licence and its `origin`: `observed` for OSM, Esri and IGN, `ai_generated` for Microsoft and Google ML footprints, `estimated` for any other dataset. Confidence 0.8, 0.6 and 0.5 by origin.
   - `overture_match_report.json`: counts, rejections, licences, and per building the facade and roof colour as tint hints. The hints are not used by default; the amendment "Overture colours as tints" below lends them behind `map.json` `"overture_tints"`.
4. **Ranking.** `heights --secondary-overrides` reads the Overture overrides as a tier of their own: an OSM `height`, an authoritative override (Catastro) height or storey count, then the Overture height (`third_party_height`), then the Overture storey count (`third_party_levels`), then OSM `building:levels`, then the estimates. Both new sources are `inferred`, never `measured`, and do not feed the neighbourhood median. The heights header lists only the Overture sources that a building used, so the attribution follows the data.
5. **Shops.** `detail --places` gives a building the Overture places inside it as shop evidence `overture`, ranked by `config/sources.json` `evidence` (ADR-022) like the OSM POIs and the Catastro use: with the default ranking (`osm`, `es.catastro`, `overture`) only a building with no OSM POI, no commercial category and no qualifying Catastro use takes them, and the first source with evidence wins whole. Places never change the facade use. Each such shop records `poi_source` (provider, GERS id, dataset, licence, confidence, `observed`, `third_party`), and the ground floor evidence is `overture_place`. The detail manifest attribution, and so the export package's, gains one line per dataset whose places gave a shop, with the Foursquare copyright notice when it applies.
6. **`overture` is a source plugin (ADR-018) that covers the world**, with `produces` `use` so that `evidence` must rank it. `sources.world.overture.OverturePlugin`, registered after `es.catastro`, adds `overture` (fetch, the download stage) and `overture-match` (reading the latest scene, so the Catastro sub-buildings in Spain). `run --no-source overture` stores `"sources": {"overture": false}`. Its licence record is ODbL 1.0 (buildings); the place licences (CDLA Permissive 2.0, Apache 2.0, CC0 1.0) are on the `config/sources.json` allowlist, and `overture match` drops a place whose licence is not on it (`licence_not_allowed`), so a record without a licence is never used. It keeps the `overture` rank in `priority`, but its overrides do not join the ADR-018 merge: a merged `height_m` becomes an authoritative override (step 1a) above an OSM `height`. So that `priority` stays the one ranking, `run` stops at the plan when it ranks `overture` above a plugin of the map that writes authoritative overrides. `SourceSteps` gains `secondary_overrides` and `places`, which `run` passes to `heights --secondary-overrides` and `detail --places`.

## Measurement

So Overture adds shops in every city tried, on about as many buildings as OSM (fewer where a Catastro use or a commercial category ranks above it), and in these three maps no heights: where Catastro runs it outranks Overture, and elsewhere the Overture heights found were copies of OSM. The height tier is there for cities where Overture carries Esri, IGN or ML heights that OSM lacks.

## Consequences

- A new network dependency at map creation: 1 min 46 s to 1 min 56 s per map in the three runs above, almost all of it reading the footers of the 512 building files; the places theme is a small part of it.
- BrightQuery places come from business registers. At confidence 0.7 and with a mapped category they are kept, but a registered office may sit on an upper floor; the shop is still placed on the ground floor of its building.
- A buildings extract is ODbL (OSM and Microsoft) plus CC BY 4.0 (Esri, Google, IGN): a scene that uses an Overture height inherits those attributions. A place keeps its record's licence: CDLA Permissive 2.0, Apache 2.0 (Foursquare, with its NOTICE) or CC0. `docs/legal/data-sources.md` records them.
- After `cadastre split`, the Catastro sub-buildings rarely match an Overture footprint (their outlines are cut from Catastro parts), so in Spain Overture mostly fills unsplit buildings, below the Catastro storeys.
- Tests never use the network: the S3 glob is replaced by a synthetic parquet written at test time (`tests/overture_fixture.py`).

## Amendment — Read only the files that meet the map (1 November 2026)

`overture fetch` opened every file of a theme with a glob, 512 for buildings and 16 for places, reading each Parquet footer over the network. It took 1 min 30 s on a good link and more than 10 minutes on another, silently. It now reads the release's STAC index first, `https://stac.overturemaps.org/<release>/collections.parquet` (about 150 KiB, one row per file with its `bbox` and S3 href), and gives DuckDB only the files whose bbox meets the map. Every href must be a Parquet file of that release, theme and type on the Overture bucket, or the fetch fails.

Measured on Murcia (37.99521, −1.137511, r90, margin 5 m): 1 of 512 building files and 1 of 16 place files, 13 s instead of 1 min 30 s, and both output files are byte-identical to the glob read (same SHA-256).

The sidecar gains `files`, `file_selection` (`stac_index`; `glob` when the index cannot be fetched, with a warning, since it is only slower; `source` for a given path; `unrecorded` in an older sidecar) and `files_in_theme`. `overture fetch` prints `files 1 of 512`. If no file meets the map, one file is read so the output keeps its schema with no rows.

## Amendment — Overture colours as tints (plan C2, 8 November 2026)

Status: proposed until the headset check below. Off by default.

Decision 3 recorded the facade and roof colours of a matched footprint as tint hints and left them unused. With `map.json` `"overture_tints": true` they become wall and roof tints through the ADR-023 path (decision 7). With the key absent or false nothing changes: no flag is passed, no file is written, and every output stays byte-identical.

1. **A pairing of its own.** `overture match --tints` writes `overture_tints.json` (`onward_generator.overture_tints` 0.1.0). It does not reuse the height pairing. A row that lends no height or floors is dropped before that pairing, and a row with only a colour must still take part. Changing the height pairing could also move `heights_overrides.overture.json`. So a second greedy pass runs with the same rule: best intersection over union first, at least `min_iou`, each footprint used once on either side, and a tie keeps row order, then id order. Every polygon row with at least one colour that may be lent takes part. One OSM building can therefore take its height from Overture row A and its colour from row B. Each value names its own GERS id. `heights_overrides.overture.json`, `overture_places.json` and `overture_match_report.json` (with its `tint_hints`) are unchanged with or without `--tints`.
2. **One colour at a time, observed only.** The dataset of each colour is its own `/properties/facade_color` or `/properties/roof_color` source, else the whole-record source. The refusals, in this order and counted per colour value under `counts.skipped`, are:
   - `skipped_dataset`: the dataset is in `skip_datasets` (OpenStreetMap). The extract already has the tag.
   - `licence_not_allowed`: the licence is not on the `config/sources.json` allowlist, so `unknown` is refused too.
   - `origin_not_observed`: the dataset is not `observed` in `origins`. The ML footprint datasets are `ai_generated` and any unlisted dataset is `estimated`. Such a colour is refused, never recorded as an estimate.
   - `colour_unparseable`: `parse_colour` cannot read the value as a CSS name, `#rgb` or `#rrggbb`.

   A row whose colours are all refused does not take part in the pairing. A row that takes part and pairs with nothing is `unmatched`. Each `tints[]` entry is `{building_id, gers_id, iou, facade?, roof?}`, and each colour is `{colour, dataset, license, origin: "observed", attribution}`.
3. **Below every OSM tag.** `detail --overture-tints` checks the schema, the local grid and that every `building_id` is a building of the scene, as `--places` does. A missing file stops `detail` with `rerun overture match --tints --overwrite`. Walls: OSM `building:colour`, then `building:material`/`material`, then the Overture `facade_color` (a tint of `plaster_white`), then the generated palette. Roofs: OSM `roof:colour`, then `roof:material`, then the Overture `roof_color` (a tint of `roof_tile` under a pitched `roof:shape`, of `roof_flat_grey` otherwise), then the template. As with an OSM `roof:colour`, an estimated hip keeps its tile. A landmark keeps its walls but may take a roof colour. Building parts and scenic shells take no colour. The parts of one Catastro parcel share their wall and roof (`appearance_key`). The first part in id order with a facade colour lends it to the whole parcel, and separately the first part with a roof colour.
4. **Provenance.** `facade.materials.wall_source` and `roof_source` name `overture:facade_color` and `overture:roof_color`, with origin `observed`. `wall_evidence` and `roof_evidence` (`provider: overture`, GERS id, dataset, licence, origin, colour, IoU) are added only where the lent colour chose the material. The building's visual node carries `tint_source: "overture"` when every tint on it came from Overture. `panoramax apply` then records `overture_colour` in `tint_skipped` instead of `osm_colour`. `detail_report.json` gains `counts.third_party_tints`:
   - `matched`: the entries of this scene.
   - `walls` and `roofs`: the buildings whose material a lent colour decided. Each Catastro part counts.
   - `by_dataset`: those materials by dataset.
   - `not_used`: the colours that decided nothing, by reason: `osm_tag`, `landmark`, `scenic`, `estimated_roof` or `no_tint_material`.

   The attribution gains one line per Overture dataset whose colour a building took. It is merged with the places lines and sorted.
5. **Pipeline.** The plugin adds `--tints` to `overture match` and passes `detail --overture-tints` only when the switch is on. The file is then the stage's marker, so switching the option on runs the match again, and heights and every later stage follow it. Switching it off does not make `detail` stale: rerun from `detail` (`run --from detail`) to drop the tints.

**Measured.** All four bench maps lend nothing. `task bench -- run --offline --overture-tints` against the run with the option off shows a delta of 0 in triangles, draws and lightmap pages. Every Overture colour there comes from OpenStreetMap: Madrid refuses 50 colours (`skipped_dataset`), Paris 1, Kraków 132 and Murcia has none. Those colours are already in the extract. On the synthetic block of `tests/integration/test_overture_pipeline.py`, one Esri wall and roof add 3 draws (29 → 32 after `materials apply`). The tinted wall is listed under `trim.kept_materials` and stays off the atlas (ADR-020).

**Before it is turned on by default:**
- Find a real city where Overture colours come from a dataset other than OSM, so the option has a measurable effect.
- On the headset, check that a tinted wall and a tinted roof read as their colour under the baked light, beside palette walls and trim-atlas facades.
- Check that fixed views A and B stay within 150 draws.
